OAuth 2.0 Attested Agent Identity

Abstract

This document profiles OAuth 2.0 Attestation-Based Client Authentication for identifying agents. It defines an attested agent identifier for agents that share an OAuth client, the identifier's namespace, profile selection, verifier processing, and attester trust restrictions. Authorization policy and mapping to a governed principal remain with the consuming authorization profile.¶

1. Introduction

One OAuth client can host several agents. Authenticating that client does not identify which agent is operating. This profile adds the attested_agent_id claim to a Client Attestation and defines the resulting authenticated identity. It uses the additional-claim facility in [ATTEST], Section 4 and profiling rules in [ATTEST], Section 13; base ATTEST authentication continues to apply.¶

A verifier returns either an attester/client pair for an agent with its own client, or an attester/client/agent tuple for a shared client. These results can be consumed without an agent-federation protocol. Neither establishes permission to act for a user or access a resource.¶

2. Conventions and Terminology

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [BCP14] (RFC2119) (RFC8174) when, and only when, they appear in all capitals, as shown here.¶

Client Attestation, Client Attester, and Client Instance follow [ATTEST]. A verifier is an authorization server or resource server validating an attestation. An agent is a software principal identified by a consuming application. OAuth errors follow [RFC6749], JWT claims follow [RFC7519], and DPoP follows [RFC9449].¶

Support for each mode is OPTIONAL. An implementation claiming a mode MUST apply its requirements below and ATTEST's validation rules.¶

3. Profile Selection

The verifier MUST determine profile applicability from trusted configuration for its tenant context, approved attester, and OAuth client. Before accepting requests, that configuration MUST identify:¶

  • Whether the client identifies one agent or hosts several agents using the shared-client mode in Section 5.¶

  • The permitted attesters and their authorized client and agent namespaces.¶

  • The accepted ATTEST authentication methods and proof algorithms.¶

The client MUST be provisioned with the applicable mode and accepted methods before using this input. An unauthenticated client identifier can locate configuration, but MUST NOT establish its authority; the verifier MUST confirm the client identity through ATTEST validation. Presence or absence of an agent claim MUST NOT switch modes. A failed shared-client request MUST NOT fall back to an own-client mapping.¶

This is the out-of-band profile-selection mechanism permitted by [ATTEST], Section 13. ATTEST metadata advertises its authentication capabilities; it does not by itself advertise this attested-agent profile. No new discovery field is needed for these configured relationships.¶

4. Agent with Its Own Client

The verifier MUST authenticate the client under ATTEST. It MUST identify the attester from the configured authority associated with the trusted key that validated the attestation, even when iss is absent. If a key is associated with multiple authorities, configuration MUST select one unambiguous authority for this client and tenant before accepting it. An iss claim, when present, MUST match that authority's identifier.¶

The authenticated identity is the pair of that attester identifier and client sub. A consuming authorization profile can map the pair to its own governed principal. An attested_agent_id claim, if present, MUST NOT switch this mode or override that pair.¶

5. Agent Behind a Shared Client

This document defines the attested_agent_id JWT claim for agent evidence in a Client Attestation. Its value is a non-empty, case-sensitive string identifying one agent in the namespace of the attester and OAuth client. The attester MUST NOT reassign that value to a different agent within that namespace.¶

The claim asserts that the Client Instance represented by the attestation is authorized to authenticate as that agent using the attestation's confirmation key. It does not assert user delegation, resource authority, or an independently verified execution identity. Its value is an external identifier. Mapping it to an authorization principal belongs to the consuming authorization profile.¶

An attester issuing a shared-client attestation for this profile MUST:¶

  • Include attested_agent_id and an iss identifying the attester in the integrity-protected claims set of the Client Attestation JWT.¶

  • Use a non-empty StringOrURI value for iss that matches the approved attester identifier in the verifier's trusted configuration.¶

  • Retain the OAuth client identifier in sub and the Client Instance Key in cnf.jwk, with their ATTEST meanings.¶

The verifier MUST:¶

  1. Validate the Client Attestation and the selected ATTEST proof before using its agent claim. An agent identifier carried only in the request or proof is not attester-authenticated agent evidence.¶

  2. Validate iss and attested_agent_id as required above. The key validating the attestation MUST be authorized for that exact iss; the claim MUST NOT authorize discovery of a new attester.¶

  3. Return the exact tuple (iss, sub, attested_agent_id) as the authenticated agent identity to the consuming profile. The verifier MUST check that the attester is authorized for that client and agent namespace. If an attester/client pair serves several platform tenants, its agent identifiers MUST distinguish them; otherwise distinct attester namespaces MUST be used.¶

  4. Use the confirmation key from that same validated attestation for ATTEST proof validation. Claims from separate attestations MUST NOT be combined to construct an agent identity or key association.¶

A base ATTEST implementation can ignore this additional claim. Such an implementation does not support shared-client agent identification. The claim is required by this selected profile, not by base ATTEST.¶

6. Verification Failures

In either mode, a missing, empty, or incorrectly typed required claim, an unapproved attester, or an invalid attestation/proof MUST cause rejection. For a profile-specific claim validation failure, the verifier MUST return invalid_client_attestation; other ATTEST failures retain ATTEST's error and challenge processing. A valid attestation does not imply authorization. A consuming profile that denies access MUST use its applicable authorization error.¶

7. Proofs, Renewal, and Compatibility

The configured ATTEST method MUST govern proof processing. In attest_jwt_client_auth_dpop mode, the client and verifier MUST use ATTEST's combined mode, including its key-matching and nonce rules. In attest_jwt_client_auth mode, they MUST use the ATTEST PoP JWT; any accompanying DPoP proof retains its separate role under ATTEST.¶

The verifier MUST NOT treat a separately proven DPoP key as endorsed by the attester solely because it accompanies a valid attestation. When the selected grant policy requires an attested output key, the verifier MUST verify that it matches the attestation's confirmation key. Unsupported method or key combinations MUST fail; they MUST NOT trigger another authentication mode or skip a required proof.¶

For each use of a renewed or reused attestation, the verifier MUST reapply profile validation and current attester and client policy. A replacement key requires a valid attestation authorizing that key for the named agent. Neither the previous key nor an unchanged agent identifier alone establishes that authorization. Attester enrollment and evidence collection remain deployment mechanisms.¶

The additions to ATTEST are explicit:¶

Table 1
Item Requirement added by this profile
Applicability Trusted, provisioned mode selection; no claim-triggered fallback
Shared-client claims iss and attested_agent_id are REQUIRED in the attestation
Agent resolution Exact attester/client/agent tuple and authorized namespace
Trust Attester authority and client restrictions in Section 8
Proof and renewal Key-role and current-policy checks in this section

ATTEST's typ, client sub, proof formats, transport, metadata, and refresh-token binding remain unchanged. This profile does not require iat in the Client Attestation or introduce a proof method. Grant issuance and refresh permission remain with the consuming profile.¶

8. Attester Trust and Client Restrictions

The verifier MUST configure which attesters may assert which client and agent namespaces in each verifier tenant. Signature verification alone MUST NOT grant an attester authority over every agent namespace.¶

A client administrator MAY restrict the acceptable attesters through the authenticated registration or configuration process. Such a restriction is the client's endorsement for this profile; it is not a new ATTEST message. The verifier MUST:¶

  • Authenticate the party configuring the restriction and verify its authority over that client registration.¶

  • Accept an attester only within both the verifier's approved trust scope and any configured client restriction. An empty intersection MUST prevent acceptance; absence of a client restriction leaves the verifier's approved set in effect.¶

  • Apply current approved restrictions before accepting an attestation. Cached configuration MUST have a finite freshness limit; stale data MUST NOT authorize acceptance. Request-supplied metadata MUST NOT expand or replace the approved set.¶

These rules are sufficient for configured deployments. Interoperable discovery of client restrictions, if later needed, can be defined as a separate extension without changing ATTEST or blocking this profile.¶

9. Security Considerations

The security considerations of ATTEST apply. The verifier relies on the attester to verify the agent affiliation and key authorization it asserts. Its signature protects that assertion; it does not independently prove the underlying platform evidence. Enrollment and evidence collection remain deployment mechanisms.¶

If agents share a private key, its holder can use any valid attestation issued for that key. Deployments requiring isolation between agents need separate key control and attester policy that enforces it. A new agent identifier or a renewed attestation does not itself prove execution continuity, prevent cloning, or authorize key replacement.¶

An attester's compromise permits assertions within its trusted scope. Verifiers SHOULD minimize that scope and audit changes to trust policy. Attestation and proof freshness retain their ATTEST meanings; this profile creates no exception to challenge or replay checks.¶

10. Privacy Considerations

The agent identifier can correlate activity across verifiers that receive it. Attesters SHOULD use identifiers without embedded personal information. Verifiers SHOULD retain and disclose the identifier only as needed for the consuming profile's purpose. A consuming profile can expose a different governed identifier downstream while retaining the authenticated tuple for local resolution.¶
